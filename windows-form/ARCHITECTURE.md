# Архитектура Budget Tracker

Проект разделён на независимые блоки, чтобы интерфейс, расчёты и способ хранения
данных можно было изменять отдельно.

## Блоки

| Блок | Файл | Ответственность |
|---|---|---|
| Доменная модель | `BudgetTracker/DomainModels.h` | Операция, категории, лимиты и единый снимок данных |
| Изменение данных | `BudgetTracker/BudgetService.h` | Добавление, редактирование и удаление операций, переименование категорий |
| Финансовая логика | `BudgetTracker/FinanceService.h` | Баланс, доходы/расходы, агрегация, траты по категории |
| Проверка ввода | `BudgetTracker/InputValidator.h` | Проверка сумм и очистка пользовательского текста |
| Регулярные платежи | `BudgetTracker/RecurringPaymentService.h` | Создание наступивших ежемесячных операций и расчёт следующей даты |
| Прогноз | `BudgetTracker/ForecastService.h` | Прогноз баланса до конца текущего месяца |
| Отчёты | `BudgetTracker/ReportService.h` | Формирование подробного текстового отчёта |
| Личный профиль | `BudgetTracker/DomainModels.h`, `MyForm.h` | Имя, валюта, месячный бюджет и финансовая цель |
| Контракт хранения | `BudgetTracker/IDataStorage.h` | Общие операции `Load` и `Save` |
| PostgreSQL | `BudgetTracker/PostgreSqlStorage.h` | Таблицы и сохранение через транзакцию |
| Конфигурация | `BudgetTracker/StorageFactory.h` | Выбор хранилища и чтение строки подключения |
| Представление | `BudgetTracker/MyForm.h` | Только управление формой и реакция на действия пользователя |

## Как выбирается хранилище

1. Приложение ищет переменную окружения `BUDGETTRACKER_POSTGRES_CONNECTION`.
2. Если её нет, читает `PostgreSqlConnection` из `storage.config` рядом с `.exe`.
3. Если строка подключения не задана или PostgreSQL недоступен, приложение
   показывает ошибку и блокирует работу с финансовыми данными.

Приложение сохраняет данные только в PostgreSQL. Файлового резервного режима нет.

### Зачем в проекте PostgreSQL

PostgreSQL является обязательным хранилищем приложения и обеспечивает:

- несколько пользователей и авторизация;
- одновременная работа с разных компьютеров;
- быстрый поиск и отчёты по большому числу операций;
- связи между пользователями, счетами, долгами и семейными бюджетами;
- централизованное резервное копирование;
- демонстрация работы с СУБД в курсовой.

## Удалённая Supabase и разделение пользователей

Все установки используют одну удалённую PostgreSQL в Supabase. При первом
запуске приложение создаёт случайный UUID и сохраняет его в:

```text
%LocalAppData%\FinancialAssistant\client_id.txt
```

Новая база при каждом запуске не создаётся. Один и тот же компьютер продолжает
использовать прежний UUID. Во всех таблицах есть колонка `client_id`, а загрузка,
удаление и запись выполняются только для текущего UUID. Поэтому данные разных
установок не смешиваются.

Для подключения текущего компьютера запустите `Настроить Supabase.cmd`, введите
пароль базы Supabase и перезапустите приложение.


## Реализованный новый функционал

### Личный профиль

Профиль содержит имя пользователя, основную валюту, месячный бюджет и финансовую
цель. Текущий положительный баланс используется как прогресс цели. Информация
профиля сохраняется в том же хранилище, что и финансовые данные, и попадает в
текстовый отчёт.

### Регулярные платежи

На отдельной вкладке можно создать ежемесячный доход или расход:

- выбрать тип и категорию;
- указать сумму и день месяца;
- добавить комментарий;
- посмотреть следующую дату;
- удалить ненужный шаблон.

При запуске приложение автоматически создаёт все операции, дата которых уже
наступила. После создания следующая дата переносится на месяц вперёд. Для 29–31
числа в коротком месяце используется последний доступный день.

### Экспорт отчёта

Кнопка находится на вкладке «Статистика». Период берётся из полей «С» и «По»
на вкладке «Операции». TXT-отчёт содержит:

- общие доходы, расходы и итог;
- суммы по категориям;
- перечень операций;
- прогноз до конца текущего месяца.

### Прогноз

Прогноз отображается на вкладке «Статистика». Он рассчитывается как:

1. текущий общий баланс;
2. минус ожидаемые обычные расходы до конца месяца;
3. плюс будущие регулярные доходы текущего месяца;
4. минус будущие регулярные расходы текущего месяца.

Обычные расходы прогнозируются по среднему расходу за прошедшие дни текущего
месяца. Уже созданные регулярные операции исключаются из среднего, чтобы они не
учитывались дважды.

## Подключение PostgreSQL

На компьютере найден запущенный PostgreSQL 18, но PostgreSQL ODBC Driver
(`psqlODBC`) не установлен. После установки 64-битного драйвера:

1. Создайте базу:

   ```sql
   CREATE DATABASE budget_tracker;
   ```

2. Скопируйте `storage.config.example` в каталог с `BudgetTracker.exe`,
   переименуйте в `storage.config` и укажите пользователя/пароль.
3. Запустите приложение. Таблицы будут созданы автоматически.

Для Debug x64 каталог приложения: `x64/Debug`.

Пароль безопаснее передавать через переменную окружения:

```powershell
$env:BUDGETTRACKER_POSTGRES_CONNECTION =
  'Driver={PostgreSQL Unicode(x64)};Server=localhost;Port=5432;Database=budget_tracker;Uid=postgres;Pwd=ваш_пароль;'
```

## Варианты развития курсового проекта

### Вариант 1 — расширенная аналитика

- отчёт по месяцам и годам;
- сравнение текущего месяца с предыдущим;
- линейный график динамики баланса;
- экспорт отчёта в CSV/PDF;
- поиск и фильтрация по категории, типу и тексту комментария.

Сложность: средняя. Хорошо подходит, если главная тема работы — анализ данных.

### Вариант 2 — планирование личного бюджета

- месячные лимиты вместо бессрочных;
- финансовые цели и прогресс накопления;
- регулярные операции;
- прогноз остатка до конца месяца;
- уведомления при достижении 80/100% лимита.

Сложность: средняя. Лучший баланс между объёмом, пользой и наглядностью.

### Вариант 3 — счета и кошельки

- несколько счетов: наличные, карта, вклад;
- начальный баланс каждого счёта;
- переводы между счетами;
- отдельная статистика по каждому счёту;
- учёт валют и курсов обмена.

Сложность: средняя/высокая. Добавляет хорошую предметную модель и новые связи БД.

### Вариант 4 — долги и совместные расходы

- учёт выданных и полученных долгов;
- сроки возврата;
- разделение чека между участниками;
- статусы «ожидает», «частично возвращён», «закрыт»;
- напоминания о задолженности.

Сложность: средняя. Необычный вариант, который выделит проект среди типовых.

### Вариант 5 — многопользовательская система

- регистрация и авторизация;
- отдельные кошельки пользователей;
- роли пользователя и администратора;
- семейный бюджет с общими и личными операциями;
- журнал изменений;
- резервное копирование и восстановление.

Сложность: высокая. Лучше выбирать, если PostgreSQL является важной частью задания.

### Вариант 6 — умный помощник

- автоматическое определение категории по комментарию;
- поиск аномально крупных расходов;
- рекомендации по сокращению затрат;
- прогноз расходов следующего месяца;
- импорт банковской выписки CSV.

Сложность: высокая. Можно начать без машинного обучения — с правилами и средней
суммой расходов, а интеллектуальную часть добавить как развитие.

### Вариант 7 — календарь платежей

- календарное представление операций;
- ближайшие обязательные платежи;
- цветовые отметки просроченных платежей;
- напоминания за несколько дней;
- перенос платежа на другую дату.

Сложность: средняя. Особенно хорошо сочетается с уже реализованными регулярными
платежами.

### Вариант 8 — импорт банковских выписок

- загрузка CSV;
- предварительный просмотр;
- автоматическое сопоставление колонок;
- обнаружение дубликатов;
- правила автоматического выбора категории.

Сложность: средняя/высокая. Даёт проекту практическую ценность.

### Вариант 9 — финансовое здоровье

- размер финансовой подушки в месяцах;
- доля обязательных расходов;
- коэффициент сбережений;
- оценка стабильности бюджета;
- персональные рекомендации.

Сложность: средняя. Можно реализовать прозрачными формулами без искусственного
интеллекта.

### Вариант 10 — семейный бюджет

- приглашение участников;
- общие и личные счета;
- общий месячный лимит;
- распределение расходов по участникам;
- история действий.

Сложность: высокая. Здесь PostgreSQL становится действительно необходим.

## Рекомендуемый состав курсовой

Практичный вариант без чрезмерного разрастания:

1. месячные лимиты;
2. финансовые цели;
3. регулярные операции;
4. несколько счетов;
5. отчёт по месяцам;
6. экспорт в CSV;
7. PostgreSQL с резервным текстовым хранением.

Такой набор показывает декомпозицию, работу с базой данных, бизнес-логику,
отчётность и отказоустойчивость. Если сроки ограничены, сначала стоит реализовать
месячные лимиты, цели и отчёт по месяцам.
